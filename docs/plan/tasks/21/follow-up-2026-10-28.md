## PULL-анализ

Точное определение PULL из исходного плана не предоставлено. Проверены доступные
технические значения; продуктовая гипотеза ниже явно отделена от фактов.

- **Git pull от клиента к Orion:** `authorizedUserCanPushCloneAndPullRepositoryOverSsh`
  прошёл в сохранённом SSH E2E и независимом focused повторе выше. Он создаёт commit,
  делает SSH push, clone, второй
  push и `JGit pull`, затем проверяет содержимое. Это положительный сценарий
  реального SSH transport с JGit, не отдельный OpenSSH CLI и не доказательство
  всех вариантов merge/rebase, dirty worktree или конфликтующей истории.
- **Fast-forward контракт матрицы:** `GitCliWorkflowClient.pull` вызывает
  `git pull --ff-only`; `OrionGitWorkTree.pull` делает fetch, проверяет ancestry
  и отклоняет non-fast-forward. Оба находятся в test-support/adapters. Нельзя
  выдавать эти адаптеры за готовый production background-sync.
- **Автоматический pull upstream в Orion:** задача `07_external-git-repository-sync`
  оставляет outbound/retry/audit и inbound replication незавершёнными. Лист
  `01_primary-upstream.md` имеет чужой Owner; takeover не выполнялся. Для preview
  исключить обещание автоматического bidirectional mirroring до реализации и
  проверок restart, conflict preservation, auth failure и bounded retry.
- **Pull requests:** список открытых PR GitHub пуст. Нет открытого PR, которому
  можно присвоить результат review; закрытые/исторические PR не анализировались.
- **Продуктовый pull/спрос:** рабочий транспорт не доказывает спрос. Гипотеза —
  self-hosted Git для команды, которой нужны контроль данных и управляемые ACL.
  Проверяемый следующий шаг — внешний оператор устанавливает архив по quick start,
  выполняет push/clone/pull и отказ read-only push, затем фиксирует необходимость
  продукта, сложность эксплуатации и готовность продолжать использование.
  Реального интервью, внешнего тестера и подтверждения оплаты здесь нет.

## Передача разбора SegmentCompressionTest

По явному решению пользователя исправление передано другой сессии. Здесь не
сохраняется изменение Java-кода. Временные `RepeatedTest(40)` и diagnostic assertion
удалены; параллельные изменения payload до 4096 сохранены и принадлежат другой сессии.

Команды этой диагностики:

```sh
make test MODULE=agent/agent-session-server TEST='SegmentCompressionTest#finalContentVerificationDoesNotHoldTheSessionLock' LOG=/tmp/orion-segment-lock-focused.log
make test MODULE=agent/agent-session-server TEST=SegmentCompressionTest LOG=/tmp/orion-segment-compression.log
make test MODULE=agent/agent-session-server TEST='SegmentCompressionTest#finalContentVerificationDoesNotHoldTheSessionLock' LOG=/tmp/orion-segment-repeat.log
```

Первый focused запуск прошёл. Весь класс: 39 passed. Временные 40 повторов прошли
после параллельного уменьшения payload, поэтому это не доказательство исправления
исходного 128 КБ сценария. В `/tmp/orion-segment-diagnosis` создана отдельная Java-копия
исходного сценария с 128 КБ, скомпилированная `javac -cp <surefire classpath> -d <dir>`
и вызванная через `java -cp <dir>:<classpath> pro.deta.orion.agent.server.journal.CompressionDiagnosis`.
Все 10 вызовов прошли: холодный 7198 ms, последующие 502–637 ms. Это обход JUnit runner
для диагностики, а не замена штатной проверки. Обнаружена чувствительность к прогреву;
точная причина исходного превышения 10 секунд не доказана, production deadlock не подтверждён.

К завершению этой проверки другая сессия создала коммит `732d5f1d`
(`native-access: Bound fixture size in journal concurrency tests`). Он не входит
в проверенный здесь baseline `c815f210`. Наличие нового коммита не делает старые
отчёты зелёными: полный release gate нужно повторить на выбранном итоговом SHA.
