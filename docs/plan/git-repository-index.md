# Общий индекс Git-репозитория и отдельное хранилище

Дата: 2026-09-29.

Документ фиксирует договорённости по архитектуре и последовательности изменений.
Он описывает целевой результат, а не утверждает, что все изменения уже реализованы.

## Цель и исходная проблема

Разделить хранение байтов и поиск данных. Сейчас storage и индексы отдельных pack
смешивают эти обязанности, а идентификатор pack зависит от checksum, который при
потоковой загрузке ещё неизвестен.

Нужен один логический индекс на репозиторий, независимый от способа хранения байтов.
Он позволяет записывать и индексировать проверенные объекты во время загрузки,
не открывая незавершённый pack для обычных читателей.

## Границы ответственности

### GitStorageApi

Отвечает за запись и получение содержимого pack и loose objects, а также за время
жизни принадлежащих ему ресурсов. Поиск объектов по индексу, refs, ветки и теги
относятся к GitIndexApi.

Локальная реализация находится в отдельном пакете. InMemoryStorage — самостоятельная
реализация без H2, файлов и публикации pack в каталог. Общие алгоритмы Git должны
работать с обеими реализациями.

### GitIndexApi

Один интерфейс на репозиторий, наравне с GitStorageApi. Он владеет:

- refs, включая HEAD, ветки и теги;
- поиском объектов и их расположений;
- метаданными pack и поиском всех доступных pack по checksum;
- сохраняемой настройкой алгоритма хеширования репозитория;
- связью между доступным pack и его расположением в storage;
- видимостью завершённых pack для обычных запросов.

Объектная запись связывает ObjectId с packId и расположением сжатого содержимого.
Она содержит логический тип и размер объекта, размер сжатого содержимого и,
для DELTA, сведения о базе и размере delta-инструкций.

Локальный индекс и индекс в памяти реализуют одинаковые правила видимости.
Физические таблицы, сериализация и детали транзакций не являются частью этих договорённостей.

### Идентификаторы

- **packId** — внутренний неизменяемый идентификатор, назначаемый до начала загрузки.
  Он не зависит от содержимого и checksum. Для локального хранения используется
  случайное имя; расположение больше не выводится из checksum.
- **packChecksum** — checksum окончательного Git-совместимого представления pack.
  Клиенты видят этот checksum; внутренний packId в Git-протокол не попадает.
  Одинаковый checksum может соответствовать нескольким packId; выбор делает клиент.
- **Checksum входного pack** проверяет исходный поток. После resolve и формирования
  самодостаточного представления итоговый packChecksum может отличаться от входного.

Алгоритм хеширования задаётся один раз при создании репозитория и хранится в индексе.
По умолчанию используется SHA-1; явно можно выбрать SHA-256. При повторном открытии
используется сохранённая настройка. Менять алгоритм существующего репозитория нельзя.
Настройка едина для ObjectId, CommitId и PackChecksum. Сами значения хранят только
байты длиной 20 или 32; алгоритм не дублируется в каждом идентификаторе.
Индекс проверяет соответствие записываемых идентификаторов алгоритму репозитория.

## Чтение pack и проверка объектов

PackReader — самостоятельный последовательный reader, не часть GitStorageApi.
Он хранит состояние разбора и предоставляет pull-интерфейс через next.
Циклом управляет ingestor: он вызывает reader и явно обрабатывает результат.
Reader не хранит ссылку на ingestor и не вызывает его через callbacks.

Reader отвечает за разбор структуры pack и базовые проверки входного формата.
Ingestor отвечает за распаковку, вычисление ObjectId, запись содержимого,
добавление проверенных объектов в индекс и разрешение DELTA.

Сжатое содержимое переносится в storage без перепаковки там, где представление
объекта сохраняется. Распаковка для проверки не требует независимого второго
чтения исходного сетевого потока. Публичный контракт не должен заставлять вызывающий
код одновременно управлять двумя связанными потоками — сжатым и распакованным.
CompressedGitObjectRead не добавляется только ради предполагаемой дедупликации.

Согласованное имя смещения в PackRead — packOffset. Оно обозначает начало сжатого
содержимого относительно начала pack, поглощаемого PackReader, а не абсолютную
позицию внешнего потока. При записи в новый внутренний формат отдельно учитывается
фактическое расположение байтов в storage; входные смещения нельзя переносить туда
без преобразования.

Метаданные должны ясно различать objectSize и compressedSize. Для DELTA размер
инструкций отличается от размера восстановленного объекта. Ограничения времени
жизни содержимого текущей записи описываются коротким комментарием контракта.
Окончательная форма возвращаемого значения next уточняется при реализации;
отдельная публичная абстракция чанков ByteBuffer не является обязательным требованием.

## Жизненный цикл загрузки

1. Назначить packId и начать запись содержимого в storage. Итогового checksum
   и окончательного количества записей в этот момент может ещё не быть.
2. Последовательно читать входной pack. Сжатые записи сразу переносить в storage
   как есть, параллельно выполняя проверки и собирая необходимые метаданные.
3. Для обычного объекта распаковать содержимое, проверить размер и вычислить
   окончательный ObjectId. Сразу добавить проверенную запись в общий индекс.
   После этого временные ресурсы объекта можно освободить: для будущего resolve
   содержимое уже доступно в storage, держать его целиком в памяти не требуется.
4. DELTA также можно сразу записать в storage, но объектная запись с окончательным
   ObjectId появляется в индексе только после полного resolve и проверки результата.
   Сохранить сведения, необходимые для последующего разрешения таких записей.
5. Накапливать соответствие входных смещений и ObjectId проверенных объектов.
   Преобразовывать ссылки OFS_DELTA на базы в ссылки по ObjectId, как только база
   разрешена. Неразрешённые цепочки остаются задачей этапа resolve.
6. Дочитать и проверить checksum исходного pack. Только после успешной проверки
   выполнять завершающий этап разрешения DELTA, включая цепочки и внешние базы.
7. После полного resolve обеспечить самодостаточность итогового pack: необходимые
   базы должны входить в его представление. К этому моменту известно число записей.
8. Финализировать данные в storage и вторым проходом вычислить checksum
   окончательного Git-совместимого представления. Checksum хранится в индексе;
   внутренний формат может дополнительно содержать его после финализации.
9. Опубликовать в индексе завершённый pack с checksum и сведениями о расположении.
   Несколько pack с одинаковым checksum могут быть доступны одновременно.
   Клиент может выбрать существующий pack для переиспользования.
10. Только после успешной загрузки и выбора доступного pack применять обновления refs.

Раннее добавление обычных объектов в индекс обязательно: откладывать весь индекс
до конца загрузки не нужно. Для DELTA условием добавления является полный resolve.

## Видимость, ошибки и конкуренция

Записи загружаемого pack доступны внутри загрузки по его packId. Обычные запросы
объектов и pack видят только доступные pack. Наличие уже проверенной объектной
записи само по себе не делает незавершённый pack публичным.

Ошибка чтения, неверный входной checksum или неразрешимая DELTA не публикует pack
и не меняет refs в рамках этой загрузки. Предыдущие доступные данные сохраняются.
Немедленный откат всех записей не требуется: в storage и индексе могут оставаться
мёртвые pack и скрытые объектные записи. Их проверка и очистка выполняются позже.
Реализация фоновой очистки не является условием этого изменения.

Публикация каждого pack атомарно делает доступными его метаданные и проверенные объекты.
Две конкурентные загрузки одинакового результата могут опубликовать разные packId
с одинаковым checksum. Поиск по checksum возвращает все доступные варианты.
Если существующий pack можно надёжно определить раньше, клиент может переиспользовать
его без повторной загрузки. Индекс не выбирает победителя и не требует дедупликации.

Блокировка pack по checksum на всё время загрузки не нужна. Конкретные внутренние
средства синхронизации backend не должны превращаться в обязательный GitLock
в публичном контракте. Проверка ожидаемого старого значения refs и существующая
семантика атомарного обновления нескольких refs сохраняются.

Публикация pack и обновление refs упорядочены, но не требуют одной общей транзакции:
завершённый pack может остаться доступным, даже если последующее обновление refs отклонено.

## Формат и Git-совместимость

Внутренний формат хранения может отличаться от Git pack. Он позволяет записывать
сжатое содержимое до resolve и до знания окончательного checksum и числа записей.
Размещение заголовка, метаданных и завершающих записей выбирается при реализации.

Git-совместимое представление строится через PackWriter с корректными заголовком,
ссылками на базы, количеством объектов и checksum. Для конвертации внутреннего pack
в Git-совместимый нужен отдельный tool. Экспорт и расчёт packChecksum должны
использовать одинаковые правила сериализации, чтобы клиент получил именно те байты,
для которых опубликован checksum.

Используется **новый формат без миграции** старых репозиториев. Автоматический импорт,
двойное чтение форматов и совместимые промежуточные режимы не требуются.

## Checkpoints и проверка результата

### 1. Новый GitIndexApi и реализации

Сначала закончить контракт общего индекса, разделение packId / packChecksum,
добавление проверенных объектов, запросы скрытых записей по packId, обычный поиск
и публикацию с поиском всех pack по checksum. Реализовать одинаковый контракт
в локальном индексе и индексе в памяти. Refs и сохраняемая настройка алгоритма
принадлежат индексу. Значения идентификаторов и индексы поддерживают SHA-1 и SHA-256;
подключение настройки к обработке байтов относится к следующему checkpoint.

Затрагиваемые компоненты: `git/git-parser`, пакеты `v2/index` и `v2/id`,
а также потребители переименованного типа checksum при необходимости.
Переключение рабочего пути ingestor, fetch и storage — следующий checkpoint.

Проверки: скрытый pack не находится обычным поиском; проверенные записи доступны
по packId; после публикации они видны; конкурентные публикации с одинаковым checksum
возвращаются поиском вместе; локальные данные и алгоритм читаются после повторного
открытия; прежний формат не принимается как новый; поведение refs сохранено.
Проверить SHA-1 по умолчанию, SHA-256 и запрет смешивания алгоритмов внутри индекса.

### 2. Переключение storage, ingestor, чтения и fetch

Зависит от готового контракта индекса. Перевести реальные потребители на разделённые
GitStorageApi и GitIndexApi, новый внутренний формат и описанный жизненный цикл.
Чтение, запись, resolve, файловые операции и согласование object-format в протоколе
должны использовать алгоритм репозитория, включая длины ObjectId и checksum.
Не передавать явно SHA-1 в существующие вызовы: значение по умолчанию задаётся настройкой.
Убрать поиск и refs из storage, а постоянные индексы отдельных pack заменить
общим индексом репозитория.

IndexedPack / MutableIndexedPack используются как различие чтения и построения
только там, где оно нужно потребителю. Они не должны сохранять второй независимый
источник истины об объектах репозитория. PackReader остаётся независимым от storage,
а ingestor явно соединяет разбор, проверку, запись и resolve.

Внутри изменения последовательно разобрать запись в storage, ingestion, чтение
по расположению и формирование pack в fetch. Итог должен переключить все реальные
потребители и удалить заменённый рабочий путь без адаптеров совместимости.

Затрагиваемые компоненты: `git/git-parser`, `git/git-native-storage`,
`git/git-native-proxy`, Git transport и HTTP-выдача pack.

Проверки: обычные объекты индексируются до завершения входного потока; DELTA —
после resolve; OFS_DELTA, REF_DELTA, цепочки и внешние базы разрешаются корректно;
ошибочный checksum не публикует данные и refs; обрыв оставляет только скрытые записи;
параллельные загрузки могут публиковать одинаковые pack; fetch и чтение работают
с обоими backend и обоими алгоритмами;
InMemoryStorage не использует файлы или H2.

### 3. Tool экспорта Git-совместимого pack

Зависит от внутреннего формата и общего пути сериализации PackWriter.
Добавить отдельный инструмент конвертации, использующий этот же путь.

Проверки: экспорт принимается стандартным Git, содержит ожидаемые ObjectId,
самодостаточен, а checksum совпадает с опубликованным packChecksum.
Проверить пустой pack, обычные объекты и pack с DELTA для SHA-1 и SHA-256.

## Состояние на момент записи

Разделение refs и storage уже было выполнено отдельным изменением.
Реализованы общий объектный индекс в памяти и локальный индекс, независимый PackId,
PackChecksum, скрытые записи и атомарная публикация pack. Поиск по checksum допускает
несколько pack. Алгоритм репозитория сохраняется в индексе; SHA-1 используется по
умолчанию, SHA-256 поддерживается значениями идентификаторов и новым индексом.

Целевые проверки индекса, идентификаторов и refs, а также полный `make test` прошли.
Рабочие пути обработки байтов пока используют SHA-1 и прежний storage API.
Следующая задача — переключить storage, ingestion, чтение, fetch и протокол на
новый индекс и настройку алгоритма; затем добавить инструмент экспорта.
