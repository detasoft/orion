# AgentD Orchestration Service

## Goal

Build `agentd` as a long-lived process on a CI/CD machine. It connects local
`session-host` processes to the central server, orchestrates sessions, and
transports durable journal events. It never owns the PTY or the agent process
tree, and a restart of `agentd` must not restart or stop any session.

```text
agentd restart != session restart
```

The implementation may begin as one Maven module with explicit package
boundaries. Separate Maven modules should be introduced only when they improve
build or dependency isolation.

## System Boundary

```text
                         central server
                               ^
                               | HTTP/2 over TLS
                        +------|------+
                        |    agentd   |
                        | orchestration
                        | transport  |
                        | journal sync
                        +------|------+
                               |
                    local control and files
                 +-------------+-------------+
                 |             |             |
           session-host  session-host  session-host
                 |             |             |
                PTY           PTY           PTY
                 |             |             |
              Claude         Codex          shell
```

Ownership is deliberately split:

- `session-host` owns execution, terminal I/O, the child process tree, local
  control, and the durable session journal.
- `agentd` owns machine registration, server connectivity, local session
  orchestration, journal synchronization, and command routing.
- the central server owns global scheduling state and the authoritative remote
  journal acknowledgement position.

The journal is durable session history. HTTP/2 is disposable transport. A
network outage or `agentd` failure must not apply backpressure to the hosted
process or prevent its journal from growing.

## Responsibilities

AgentD is responsible for:

- stable machine identity, per-process instance identity, registration,
  reconnect, heartbeat, capabilities, status, and graceful shutdown;
- discovery of local session directories and reconstruction of in-memory state
  without depending on state saved by an earlier AgentD process;
- validated session launch through a runtime abstraction and delivery of local
  control commands to `session-host`;
- reading segmented journals, following active tails, reporting retention
  gaps, batching events, and resuming from server acknowledgements;
- isolating failures and traffic so one noisy or corrupt session does not block
  commands, heartbeats, or other sessions;
- reporting machine and runtime telemetry needed for workload placement.

AgentD is not responsible for:

- owning or emulating a PTY/ConPTY, parsing ANSI, or retaining terminal screen
  state;
- directly parenting Claude, Codex, shells, or their descendant processes;
- acting as the only copy of session history;
- blocking or terminating a session when the server is unavailable;
- interpreting every harness event type or rewriting opaque event payloads.

## Identity and Persistent State

`AgentId` is a stable provisioned identity for one machine or worker
registration. `InstanceId` is a fresh UUID for each AgentD process start. The
pair lets the server distinguish a transport reconnect from a process restart.

Persistent AgentD state is intentionally small:

```text
agent/
    identity.json
    credentials
    sessions/
```

`identity.json` contains the stable agent identity and registration metadata.
Machine credentials live in a protected file or operating-system credential
store and are never passed on a command line when a protected alternative is
available. Session state belongs to each session directory. A locally cached
sync position is only an optimization; the server supplies the authoritative
remote position after reconnect.

Provisioning uses a short-lived bootstrap token to obtain a persistent machine
credential. Logs, protocol diagnostics, process arguments, and journals must
not expose either credential or unrelated session secrets.

## Server Transport and Protocol

AgentD maintains one outbound Jetty low-level `HTTP2Client` connection over
TLS. The connection contains a long-lived control stream and logical
per-session traffic that may use separate HTTP/2 streams. Application sessions
must never use a physical HTTP/2 stream ID as their identity; reconnect creates
new streams for the same logical sessions.

The control stream is opened as `POST /agent/control` and remains
bidirectional:

```text
request DATA:  agent -> server
response DATA: server -> agent
```

Agent-to-server control messages include `HELLO`, `HEARTBEAT`, `AGENT_STATUS`,
`SESSION_STATUS`, and `COMMAND_RESULT`. Server-to-agent messages include
`START_SESSION`, `INPUT`, `RESIZE`, `SIGNAL`, and `TERMINATE`.

The first exchange negotiates the versioned Agent protocol:

```text
HELLO
    protocolVersion
    agentId
    instanceId
    agentVersion
    machineInfo
    capabilities

WELCOME
    protocolVersion
    connectionId
    configuration
```

The Agent protocol version and session journal format version are independent.
Messages use explicit bounds and validation, and unsupported versions fail the
connection without affecting local sessions. Connection loss is recovered by
application-level resume rather than by relying on HTTP/2 transport state.

Reconnect uses exponential backoff with jitter and resets appropriately after
a stable connection. AgentD keeps discovery and local bookkeeping active while
offline.

## Local Session Recovery

All sessions live below one configured root, for example:

```text
sessions/
    01KABC/
        metadata
        journal-000001.seg
        control endpoint or descriptor
    01KDEF/
        ...
```

At startup and during periodic reconciliation, AgentD scans the root, validates
metadata, locates the control endpoint, determines host liveness and recorded
child state, checks journal readability, and constructs an in-memory
`LocalSession`. The Java object is a cache; the directory is the recoverable
source of truth.

Filesystem notifications are wake-ups only. A notification causes a rescan
from the durable cursor. `OVERFLOW`, missed notifications, and AgentD restart
cause full reconciliation. A periodic rescan is always retained as a safety
net.

Failure classification is per session. Invalid metadata, a corrupt journal,
an unreachable host, or a retention gap can move one session to `DEGRADED`,
`LOST`, or `JOURNAL_GAP` without terminating AgentD or disrupting other
sessions.

## Session Launch and Local Control

The server starts a session with a validated specification containing the
session ID, command, working directory or workspace reference, environment,
initial terminal dimensions, sandbox policy, and runtime.

AgentD then:

1. validates the command, environment, workspace, runtime, and policy;
2. prepares or resolves the workspace and creates the session directory;
3. launches `session-host` through `SessionRuntime` without making the host or
   child process dependent on the AgentD lifecycle;
4. waits for durable host initialization and a usable control endpoint;
5. reports `SESSION_STARTED` and begins journal synchronization.

The initial runtime abstraction is:

```java
interface SessionRuntime {
    SessionLaunchResult launch(SessionSpec spec);
}
```

`NativeRuntime` is required for the MVP and always launches the target process
through `session-host`. `DockerRuntime`, `SSHRuntime`, and `VMRuntime` are later
implementations. The API distinguishes a workspace from a session even though
MVP workspace preparation may only resolve an existing working directory.

Unix domain sockets and Windows named pipes are hidden behind one local control
client. Short request/response connections are acceptable. Control carries
`INPUT`, `RESIZE`, `SIGNAL`, `TERMINATE`, and `STATUS`; it is never used for
journal streaming.

Each server command has a unique command ID. AgentD reports completion only
after receiving the host response. Input retries preserve the input ID so host
deduplication can provide at-most-once acceptance across control reconnects.
Expected validation and delivery errors become `COMMAND_RESULT` failures, not
AgentD crashes.

## Journal Reading and Synchronization

The AgentD reader consumes the versioned journal contract without owning the
format. It must:

- read closed and active segments, compressed blocks, and complete records at
  a partially written tail;
- move across rotation and recover after file replacement or a missed wake-up;
- seek after a timestamp cursor and expose an explicit gap when the requested
  timestamp predates retained history;
- preserve unknown event type, schema version, and payload bytes without
  semantic parsing or lossy reserialization.

Each local session has a logical journal pump. A pump reads all available
records after its durable cursor, builds bounded `SESSION_EVENTS` batches, and
sends them through session transport. Batch maximum bytes, maximum records, and
maximum latency are configurable; initial measurement should select values in
the 64-256 KiB and 10-50 ms ranges.

The server acknowledges durable receipt with:

```text
SESSION_ACK
    sessionId
    throughTimestamp
```

After reconnect, the server supplies its last durable timestamp and AgentD
resumes from the next available record. If the requested position is older
than retained history, AgentD sends `SESSION_GAP` with the requested and first
available timestamps, then continues from the first available event. Cached
local acknowledgements may reduce work but are never required for correctness.

`PROCESS_EXITED` is transported from the journal like every other event; a
transient control-socket status is not the authoritative exit record. Harness
events remain opaque envelopes so adding an event type does not require an
AgentD release.

## Scheduling, Backpressure, and Failure Isolation

AgentD uses Jetty execution facilities plus a small scheduler/executor.
Blocking journal I/O may use one virtual thread per active logical pump. It
must not allocate a platform thread for every connection or operation.

Scheduling priorities are logically:

```text
control and heartbeat    high
session commands         high
journal batches          normal and fair per session
artifact/file traffic    low and future
```

Heartbeat and commands do not share a bounded queue behind session output.
Per-session quotas and fair scheduling prevent one high-output session from
starving another. HTTP/2 per-stream flow control is useful but is not the only
isolation mechanism.

When the server is slow or offline, `session-host` continues appending to its
journal. AgentD accumulates lag by leaving its cursor behind rather than by
blocking the host. Retention may create an explicit gap. Protocol errors,
journal corruption, and command delivery failures are contained at the
narrowest possible connection or session boundary.

Graceful shutdown stops accepting new server commands, flushes bounded
outbound protocol state where possible, closes HTTP/2, closes AgentD-owned
executors and watchers, and exits without sending termination to any host.

## Machine Status and Observability

`HELLO` and periodic snapshots report the stable and instance IDs, hostname,
OS, architecture, AgentD version, CPU, memory, disk, session counts, available
runtimes, and capabilities such as PTY, ConPTY, Landlock ABI, Docker, Java,
Git, Claude, Codex, and supported sandbox modes.

Metric collection must be bounded and must not delay heartbeat. Useful logs
and metrics include connection lifecycle, registration, reconnect count,
session discovery and launch, command latency, journal lag in bytes and time,
gaps, bytes and events sent, active sessions, and protocol errors. Session and
command identifiers are included where safe; credentials and payload secrets
are excluded.

AgentD exposes no public listening port. Platform service managers such as
systemd, launchd, and Windows Service Control Manager own only the AgentD
process lifecycle.

## Package Boundaries

The initial module keeps these package boundaries:

```text
agentd.core       Agent, AgentLifecycle, AgentIdentity, configuration
agentd.protocol   messages, codecs, bounds, version negotiation
agentd.transport  AgentTransport, JettyHttp2Transport, stream lifecycle
agentd.session    SessionManager, discovery, LocalSession, control client
agentd.journal    reader, cursor, watcher, pump, sync state
agentd.runtime    SessionRuntime, NativeRuntime, workspace abstraction
agentd.platform   machine information, metrics, capabilities, services
```

Dependencies point inward through interfaces so journal, transport, and
platform implementations can be tested independently.

## Delivery Order

| Order | Task | Depends on | Deliverable |
| --- | --- | --- | --- |
| 1 | Contracts and build | none | Module, executable lifecycle, versioned messages, codecs, fixtures |
| 2 | HTTP/2 transport | 1 | TLS connection, control stream, stream lifecycle, reconnect hooks |
| 3 | Identity and registration | 1-2 | Stable AgentId, per-start InstanceId, bootstrap and credentials |
| 4 | Session discovery | 1, host contracts | Startup recovery, reconciliation, local state classification |
| 5 | Runtime and local control | 1, host process support | Native launch, workspace boundary, command client |
| 6 | Journal reader | host journal and retention | Cursor reads, compressed blocks, tails, rotation, gaps |
| 7 | Journal sync and resume | 3-4, 6 | Pumps, batching, acknowledgements, transparent envelopes, resume |
| 8 | Command orchestration | 3-5 | Server command routing, results, retries, session statuses |
| 9 | Status and resilience | 2-8 | Telemetry, fairness, backoff, failure isolation, shutdown |
| 10 | Release and acceptance | 1-9, packaged host | Service packaging and end-to-end MVP scenarios |

The generic HTTP/2 transport can proceed without provisioned identity; the
registration state machine integrates with it in the following task.
Discovery, local control, and the reader can then proceed in parallel.
Platform telemetry can begin independently and is integrated with transport
after the control stream is stable.

## MVP Boundary

The MVP includes registration and connection, local session discovery,
`NativeRuntime`, session-host launch, journal reading and forwarding, all five
server commands, durable acknowledgements, reconnect/resume, explicit gaps,
machine status, and AgentD restart recovery.

Docker execution, artifact transfer, workspace checkout, autoscaling, semantic
terminal or harness parsing, complex credential providers, and multi-server HA
are deferred. Their extension points must not weaken the execution/transport
boundary.

## Acceptance Scenarios

1. Start a shell through the server, send `echo hello`, observe ordered
   `PTY_INPUT` and `PTY_OUTPUT` records at the server, and receive command
   results only after host acceptance.
2. Run at least three sessions, kill AgentD, verify every host and child remains
   alive and journals continue to grow, restart AgentD, discover all sessions,
   resume from server timestamps, and continue input without losing available
   history.
3. Disconnect the server long enough to exercise reconnect backoff while local
   sessions continue. Restore connectivity and catch up every retained event
   without starving heartbeat, commands, or quieter sessions.
4. Keep the server offline past journal retention. Reconnect, report the exact
   `SESSION_GAP`, and continue at the first available record.
5. Corrupt or truncate one session tail and verify complete preceding records
   remain readable, that session becomes degraded, and other sessions continue
   synchronization.
6. Deliver duplicate input IDs and control reconnects without writing the same
   accepted input twice.
7. Shut AgentD down gracefully and verify no local host receives a termination
   command and all hosted process trees remain alive.
