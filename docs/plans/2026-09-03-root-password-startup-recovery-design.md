# Root Password Startup Recovery Design

## Purpose

Add an explicit startup recovery option that restores access to an Orion
installation when the generated root password is no longer available or the
root user was accidentally removed. The option must preserve repositories and
the rest of the ACL, use the configured ACL storage, expose no network service
until recovery succeeds, and print the new password once in the existing root
password format.

## Command Contract

The run commands accept `--reset-root-pass`:

```sh
orion --reset-root-pass
orion run --reset-root-pass
orion start --reset-root-pass
orion restart --reset-root-pass
```

`run` remains the default command. `start` and `restart` forward the option to
the background application process. The development Make target accepts the
same option through:

```sh
make run-server ORION_ARGS=--reset-root-pass
```

The option is deliberately one-shot command-line state. It is not an
environment variable or persisted configuration value, because either could
reset the password again on an unintended later restart.

## Startup and Storage Flow

`AppOptions` parses the option and converts it into typed runtime options bound
into the Dagger application component. The ACL service consumes the request in
its normal startup phase. The runtime already starts the executor and event
manager before ACL, and starts transports only after ACL reports success, so
HTTP, Git, and SSH cannot accept a connection with the old credentials during
recovery.

When an ACL already exists, the ACL service loads and validates the complete
snapshot and applies recovery to drafts of the original ACL files. An existing
root is rewritten only in the file that contains it. Missing-root recovery
removes canonical root definitions from every configured file and restores one
canonical graph in the primary file. The full snapshot is then saved through
the configured `AccessControlStorage`, preserving the original file partition
and unchanged file bytes. The default `local:orion` backend therefore creates
an ordinary commit on its configured ref; a `file:` backend updates its normal
XML files. The bootstrap layer does not inspect or edit storage internals.

If the ACL is missing and default ACL creation is enabled, the existing default
creation path already creates a fully privileged root user and prints its
password, so recovery does not perform a second reset. If default creation is
disabled or the existing ACL cannot be parsed, startup fails without exposing
transports.

## Existing Root User

For an existing root user, recovery preserves its email, SSH public keys, JWT
keys, role references, grant references, and other ACL data. It removes all
password credentials (`ARGON2` and legacy `SHA1`) and adds exactly one new
salted `ARGON2` credential generated by `OrionPasswordHashingService`.

The updated ACL is persisted and reloaded before the password is printed. The
password uses the existing output marker:

```text
---ROOT PASSWORD: <generated-password>
```

Mutable password buffers are cleared after hashing and output. Reusing the flag
on a later launch intentionally invalidates the previously generated password.

## Missing Root User

If no case-insensitive user ID `root` exists, recovery creates exactly one root
user with the standard root email and the new `ARGON2` password. To guarantee
that this recreated user can recover the server, it receives the canonical
full-privilege authorization graph:

```text
root -> ROOT -> CONNECT + ALL_REPOSITORY + APPLICATION_CONTROL
```

The canonical role and grants are merged from the default ACL definition. Any
existing entries with those system IDs are replaced with their canonical
definitions so the recreated root cannot inherit an accidentally restricted
or broken definition. Other users, roles, grants, and credentials remain in the
ACL. Replacing a canonical system entry may restore privileges for another user
that explicitly references that same system entry; that is consistent with
those IDs denoting Orion's root authorization graph.

If more than one case-insensitive root user is present, recovery fails closed
instead of guessing which duplicate to replace.

## Failure Behavior

- Option parsing rejects duplicate recovery flags and unsupported commands.
- ACL load, validation, hashing, persistence, or reload failure aborts startup
  before transports start.
- The plaintext password is printed only after persistence and reload succeed.
- Recovery does not delete repositories or recreate the entire ACL.
- Normal startup without the flag is unchanged and prints no existing password.

## Tests

Focused tests cover option parsing, help text, and forwarding through `start`
and `restart`. ACL service tests prove that an existing root gets a new working
password while retaining keys and authorization, and that a missing root is
recreated with full privileges without changing unrelated users. They also
cover duplicate root failure and normal startup without the option.

Bootstrap lifecycle coverage verifies that recovery completes before transports
start and that the emitted password authenticates after a restart. Makefile
coverage verifies forwarding of `ORION_ARGS` to the Maven run profile. Storage
coverage includes strict reload failure, a root in a secondary native ACL file,
and file-backed password recovery.
